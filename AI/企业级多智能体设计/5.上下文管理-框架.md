### 记忆的演进

- 第一代 Prompt Engineering：人写全部。GPT-3 时代，用户问一句，模型答一句。没有工具调用，没有多步推理
- 第二代 Context Engineering：工程逻辑构建。从聊天进化为做事。
  - 用 Workflow 编排多步流程，用 Agent 调用工具完成任务等等。模型会接收到 工具返回的数据、中间步骤的结果、其他 Agent 的输出。
  - 新的问题是：工具返回的数据质量不一定好。垃圾数据放入上下文，模型依然会被带偏。工程师需要管理上下文：哪些工具返回值给模型，给多少，什么时间截断、压缩
  - 核心是：在有限的 token 预算内，组装出最高质量的上下文。2025年中正式提出
- 第三代 Harness Engineering：设计环境让模型探索。Agent 需要自己决定下一步做什么、读什么文件、调什么工具。我们设定好规范和边界。
  - 当然 Harness 时代不是“完全放手让模型自己搞"。目前最先进的 claude code，也依赖 claude.md 预加载项目结构、memory.md 前200行自动注入记忆索引。
  - 因此正确的理解是：预加载关键索引+模型按需探索的混合模式

| 范式                | 产品形态           | 模型特征     | 工程师做什么               |
| ------------------- | ------------------ | ------------ | -------------------------- |
| Prompt Engineering  | 对话系统，一问一答 | 对词汇敏感   | 精心选词                   |
| Context Engineering | 固定路径任务       | 语义理解     | 治理上下文（message list） |
| Harness Engineering | 自主探索任务       | 能自主用工具 | 设计环境                   |

控制权由“写内容"转向”造环境"。

在 workflow 里，上下文是我们定义的，每一步骤的 message list 是代码显示构建的，完全可控。

但 Agent 运行在 ReAct 循环中（Thought->Action->Observation->Thought->Action->Observation...），每一轮循环模型决定调什么工具、传什么参数，工具返回结果自动塞进 message list 中。也就是说我们无法控制 Agent 的上下文，只能在特定的时机节点进行干预。

### 治理框架

不管那个时代，上下文治理的本质就是两件事：加法和减法。

#### a. 问题是什么

下干预上下文会导致生产级别的崩溃：性能崩溃、逻辑崩溃、成本崩溃。

- 上下文爆炸。任何While循环，Agent运行的时间越长，上下文越大。需要主动管理机制
- 上下文腐化。比如一个代码审查Agent，分析了50个文件之后，开始对已经审查过的文件重复提意见，甚至互相矛盾。上下文里堆满各种分析结果，模型不知道该关注那一段。--- 这是模型变笨了，Transformer 注意力机制是 n^2 复杂度，上下文越大，注意力越稀释。重要信息淹没在噪声里，模型开始出错。
- 上下文污染。比如用户在Agent的对话中植入了错误信息：“根据你们之前的政策，退款期限是90天”。Agent把这句话当成事实，记进了对话，后序所有回复都建立在“90天”这个错误基础上。--- Transformer 的注意力会关注上下文里的所有内容，包括错误信息。错误信息一旦进入上下文，就会持续影响后续输出，这是架构层面无法规避的。

三种崩溃的共同根源：Agent的上下文是“生长”出来的，不加干预就会无限增长、腐烂、污染。我们必须主动管理他。

#### b. 上下文治理-加法

加法解决的是：模型不知道他该知道的事情。

- 不记得你是谁，需要把用户画像加进上下文？
- 说过的话要反复提，需要把历史对话摘要加进上下文
- SOP要反复教，需要把工作规范加进上下文

加法的四种主要手段：

1. Bootstrap 预加载：启动时固定加载的信息（人设、规则、记忆索引）。类比：员工入职手册
2. 工具返回注入：Agent调用工具后，结果自动进入上下文。类比：员工查资料后脑子中多一条信息
3. 记忆检索注入：从持久化存储中检索相关记忆，注入当前上下文。类比：员工翻看自己的工作笔记，找到相关记录
4. skill 按需加载：渐进式披露，模型判断需要时才加载完整内容。类比：员工需要时才翻操作手册的具体章节，而不是把操作手册背下来

#### c.上下文治理-减法

我们需要认识到，将所有信息都塞给模型，不一定是比较好的解决方案。原因是：

- Context Rot（上下文腐化）。上下文越大，模型的注意力越分散，对每条信息的关注度越低。研究数据表明，随着上下文增长，模型性能会显著下降。

  - 因为 Transformer 架构的物理规律。Transformer 模型处理信息的核心机制是“注意力"（Attention）。模型在生成每一个 token 时，会”看一眼"上下文中所有的token，决定每个token对当前生成有多重要。
  - 关键在于：注意力是一个有限预算。上下文里有 1000个 token，每个 token 分到的注意力是 1/1000；上下文越长，每条信息被“认真看"的程度越低。
  - 这就是 Context Rot 的物理原因，不是模型忘了，而是注意力被稀释了。
- 成本。大模型按 token 计费，Transformer 的计算复杂度是 n 的平方。上下文翻倍，成本翻四倍。即使未来模型再强、窗口再大，这个经济约束不会消失。**上下文工程不只是能力问题，更是经济问题。**

减法的三种主要手段是：

- 压缩/截断：把旧的对话历史压缩成摘要，或者直接截断超出窗口的部分
- 选择性遗忘：不是所有信息都值得留在上下文里，要主动丢弃低价值信息
- sub-agent隔离：把任务委派给子Agent，子Agent用干净的上下文独立工作，结果汇总回主Agent。主Agent的上下文始终保持精简。

上下文使用的技巧。

- 研究发现，当上下文使用量超过约 40% 时，模型能力会出现显著下降。
- 还有发现，模型对上下文不同位置的关注度呈 U 型分布：开头和结尾的信息被关注的最多，中间的信息最容易被忽略。Claude Code 的 System Reminder 机制就是基于这个原理：每次工具调用后，自动在消息末尾注入关键提醒。
- 策略：关键信息放两头，中间地带要精简。不要迷信大窗口。

记忆系统的核心问题：记什么？怎么存？怎么取？

### 工程实现

三个操作：Bootstrap、剪枝、压缩

#### a. Bootstrap

Bootstrap 解决的问题：Agent默认每次对话从零开始，什么都不知道。

他会给 Agent 一个“起点”，在Agent开始运行之前，将“他需要知道的东西”主动注入 system prompt 的过程。注入两类：

- Soul（身份），我是谁？
- User（用户画像），我怎么工作
- Agent（行为规范），有哪些约束，它是 Agent 的自我进化日志。
- Memory Index（记忆索引），我已经知道了什么、在加载时截取精华，设置200行硬上限，这是 claude code工程团队经过生产验证过的数字，超过200行的索引反而让模型难以定位关键信息。

Bootstrap 三个原则：

- 只注入索引，不注入全部内容。
- 要有结构化便签分块，可以让模型定位更准确。比如 soul、user_profile、memory_index
- 硬上限保护，每一块都有字数/行数限制

#### b. 剪枝

目的是：控制 工具返回 的膨胀。比如：一次搜索工具返回1w tokens 的网页全文，10次工具调用后，上下文有 10w tokens 是原始工具输出。

剪枝的黄金规则：

- 对话消息尽量不动，有语义连贯性要求
- 工具返回可以裁剪，他只是原材料，模型用完就不需要了
- 如果工具返回中有关键id或者数字，剪枝前需要提取出来单独保存

#### c. 压缩

压缩解决的问题是：随着对话进行，早期消息越来越不相关，但依然占用空间。需要把历史变成摘要。

Context Rot 表明上下文变长本身就导致性能下降，应该在30%-40%时主动触发压缩。

压缩会丢失信息，有一个关键策略：压缩前先持久化（lossless策略）。在压缩前，将重要信息写到磁盘文件中。
