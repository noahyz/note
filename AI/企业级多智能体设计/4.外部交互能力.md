工具（Tool）是 Agent 探索世界、改变外部状态的手和脚。


### 1. 工具使用的底层逻辑

目前业界主流的工具调用范式有两种。

* Native Funcation Calling（原生函数调用）。部分大模型在底层 API 原生支持的能力。在请求大模型时，不仅传入 `Message List`，还会传入一个 `Tools List`（包含工具的名称、描述和参数 JSON Schema）。大模型在理解语义后，会直接在其底层输出特殊的标记，告诉框架：“我要停下来，请帮我调用某个工具，参数是 XXX”。注意：这是模型支持的能力，模型认为需要调用则去调用。模型训练层面的能力。OpenAI、Anthropic、Google 等在训练时专门让模型学会"什么时候输出一个工具调用结构"，这是模型的内在能力。
* ReAct范式：基于 `Thought -> Action -> Action Input -> Observation` 的文本推演循环。Agent更改了用户给模型的提示词，从而引导模型这么做。但不仅仅是改提示词，本质上是"思维框架"，核心思想是：让模型在行为前显示输出推理过程，而不是直接跳到结论。

|   维度   | Native Funcation Calling（直觉反射） | ReAct Engineering（思维链推理） |
| :-------: | ------------------------------------ | ------------------------------- |
| 性能&成本 | 速度快，token少                      | 需要思考占用token               |
|  准确性  | 单一明确场景准确性高                 | 复杂场景准确性高                |
| 可解释性 | 黑盒                                 | 可通过思考迭代                  |
| 适合场景 | 简单明确的场景                       | 不确定性高的场景                |

这两者是可以互相叠加的。现代的Agent框架（如LangGraph、AuthGen）实际上就是混合模式。用 Native FC 执行工具，但在提示词中加入 ReAct 风格的思维链引导。

Native funcation Calling 工具定义背后有框架层的代码与之绑定，模型输出调用意图后框架能真正执行；skill 只是上下文文本，没有对应的执行钩子。

### 2. Agent工具设计范式

传统 API 是给“确定的程序化代码"调用的，而 Agent Tool 是给 ”充满不确定性、基于自然语言理解的大模型" 调用的。因此设计时需要

- 保证语义完整性。大模型讨厌繁琐的多次往返组合。一件事情用一个工具做完
- 入参越简单、越扁平越好，最好都是基础类型（String, Int），因为 **每个参数都会消耗 Token 且增加模型理解失败的概率** 。更关键的是，每个参数都必须附带详尽的 **自然语言描述（Description）** ，告诉模型这个字段填什么、不能填什么。
  - 边界与默认值。告诉AI 取值范围，防止 AI 填入非法值导致工具报错
- 建设性报错。面向 Agent 的报错，必须是自然语言的“知道意见”。例如返回：`"操作失败：时间参数格式错误，你输入了 2026/01/01，请你修改为 YYYY-MM-DD 的格式后重新调用本工具。"`大模型看到这句话，立刻就能自我纠错（Self-Correction）并重试。
- 工具的描述。好的描述分为两个核心部分；
  - 规范的工具名，采用”动词+名词“的形式。名字也是重要的暗示
  - 工具描述模版。四要素：功能描述（工具是干什么的）、产物说明（调用后能获得什么）、触发时机（什么场景用）、适用边界（什么场景不能用）

多租户数据隔离与身份认证。如何保证安全问题？

解法是：隐式的上下文挂载与 Hook 拦截。在调用工具之前，进行 Hook 拦截请求，从当前上下文提取真实安全的 user_id。比如动态修改文件读写路径。这样大模型从头到尾不知道底层做了路径隔离，即降低了模型的认知负担，又保证了绝对的安全。

最佳实践：

- 不要写全能工具。破坏单一职责原则。大模型极易搞混不同 action 对应的必填参数，导致频频报错
- 参数要简单。工具的参数如果是 JSON 中套 JSON，其中的转义符会把模型绕晕。大模型在生成多层嵌套转义的字符串时，出错率呈指数级上升
- 需要具体的失败。比如工具执行报错时，直接返回一个空字符串或者 null，模型不知道发生了什么，可能会反复重试，直到达到重试阈值
- 建设性报错。捕获工具底层的所有异常，将其转化为对大模型友好的自然语言提示。告诉它“错在哪了”以及“接下来你应该尝试怎么做”。
- 精简上下文。比如 读取一个文件或查询一次数据库时，不加限制地将几万行数据、数十兆的文件直接作为工具的 `Observation` 扔回给 Agent。会瞬间撑爆大模型的上下文窗口，导致本次会话中断报错。或者模型被海量数据淹没，彻底忘记任务目标。
- 设计摘要或分页机制。面对可能返回海量数据的工具（如读大文件、查数据库），强制在工具内部实现“分页返回”或者“关键信息摘要”。

Skill 是说明如何使用工具。Native Funcation Calling 是真正的执行工具。


### 3. MCP

MCP 本质上是一个协议。定义了标准，让不同系统之间可以沟通。拆分了两端。

- MCP Client（客户端）：也就是我们的 Agent 或者 AI 应用。负责理解用户的自然语言，进行推理决策
- MCP Server（服务端）：提供底层工具和数据源的地方

只要 Server 端按照 MCP 的标准格式对外暴露了自己的能力（包含哪些工具、工具的描述是什么？参数 schema 是什么？），Client 端就能自动发现、自动理解，并动态调用这些工具，完全不需要在 Agent 的代码里编码任何具体的业务逻辑。

MCP工具是如何注入的？

- 自动握手与发现。框架会先通过 HTTP 或者 SSE（Server-Sent Events）向 服务器（`localhost:8005`） 发起请求，获取这个 MCP Server 暴露的 Tool List。
- 过滤与放越权。鲸歌我们定义的 static_filter，剥离掉 Agent 不该拥有的高危工具
- Schema 组装与上下文注入。框架将获取到的工具描述和 JSON Schema，动态生成类似 `http_localhost_8005_mcp_send_email` 这样的工具名，并将其无缝拼接到大模型的 System Prompt 中。大模型就像使用本地工具一样，毫无感知的调用远程的微服务。

最佳实践：

- MCP服务提供的工具集应该保持克制和垂直。如果工具太多，极其浪费成本，且严重干扰大模型的上下文注意力
- 保证语义完整性，在 Server 端做一定程度的业务聚合
- 保持连接。再使用 Stream/SSE 长连接模式时，后端MCP工具执行一个极其耗时的重 IO 操作，且过程中没有发送心跳。client 端会因为长时间没有收到响应而超时断开，导致任务彻底失败
- 系统安全参数不能交给模型，必须我们有正常逻辑
- 状态控制的权力下放 ：强烈建议将 MCP Server 做成 无状态的（Stateless） 。所有的业务上下文和进度状态，应该由 Client（也就是我们的 Agent 框架）来控制和记忆。
- 幂等设计。由于网络抖动和 SSE 模式的不稳定性，Client 极有可能发起重试机制。你的 MCP 工具实现必须是幂等的！建议支持 Client 在调用时传入一个 `request_id`，防止资金划拨或邮件发送等核心操作因为网络重试而被重复执行两次。


### 4. 王牌工具

三大王牌工具：文件操作、代码解释器、无头浏览器。

- 文件操作。Agent 不仅需要读取和写入文件，更关键的是具备“局部编辑"的能力。对于一个比较大的文件或报告，通过生成 Diff 差异来进行精准的局部修改。一旦掌握了这个能力，Agent 就具备了极强的条理性和规划性，能够从容应对复杂的文档编辑与代码重构任务。
- 代码解释器。面对计算复杂的数学题，或者清洗数十万行的Excel数据。Agent不再依赖单纯的“脑补推理"，而是像人一样自主编写代码，运行他，并根据输出结果进行下一步决策。极大的扩展了Agent处理数据、图表和复杂逻辑的边界。
- 无头浏览器。Agent 可以自主打开网页、滚动屏幕、点击按钮、甚至截取当前屏幕画面的快照（Screenshot）并配合多模态视觉模型进行深度分析。

注意：不要让 Agent 在宿主机上执行代码。模型产生幻觉执行有损的指令；或者如果 AI 应用对外暴露，很可能通过提示词攻击导致成为肉鸡。

业界一般使用 沙盒（Sandbox）隔离技术。一个强大的开源方案：**AIO-Sandbox**。利用 Docker 容器技术，可以隔离出一个绝对安全的独立环境。通过 MCP协议，AIO-Sanbox 将沙盒内极其丰富的工具库暴露给了外层的 Agent。沙盒不仅提供了基础的运行代码能力，还直接暴露了海量的浏览器操作原语。

最佳实践：

- 绝不允许在没有隔离环境的机器上直接赋予 Agent 运行代码的权限
- **设定严格的工具优先级** ：一定要在 Prompt（Backstory）中教育 Agent： **代码调用 API/ 第三方包 > 专业搜索工具 > 操作浏览器硬爬** 。就像在股票实战中，让它写 Python 代码调用专门的金融库（如 `yfinance`）获取数据的效率，要远远高于让它用浏览器去雅虎财经网页上一点点“抠”数据。
- **预置依赖包** ：为了提升速度和稳定性，强烈建议在你的 Docker 沙盒镜像中事先预装好常用的大型 Python 库（如 `pandas`, `requests`, `beautifulsoup4` 等），并且在 Agent 的系统提示词中明确告知它“你已经拥有了这些现成的包，请直接 import 使用”。这能省去模型反复尝试 `pip install` 的无用功。
- **潜行伪装防拦截** ：当你不得不使用无头浏览器去抓取数据时，极容易被目标网站的防爬虫机制拦截。记得在沙盒底层配置中，尽量开启“潜行模式”，伪装成真实的 User-Agent、正常的屏幕分辨率，甚至是伪造 WebGL 指纹。
- **必须使用足够强的模型** ：千万不要用便宜的小参数模型去尝试驾驭这三大超能力。规划复杂的代码逻辑和理解多步浏览器交互，对模型的智商要求极高。如果模型不够聪明，它只会在沙盒里疯狂撞墙报错，白白浪费你的时间和计算资源。


### 5. skills

工具有了，Agent 怎么去用？比如 PDF 文件有很多坑：有些 PDF 有文字层可以直接提取，有些则是扫描图片需要 OCR；有些 PDF 有密码保护；有些中文内容直接用 `pypdf` 提取会乱码，需要特殊处理。这些"最佳实践"，Agent 并不天然知道——它只知道"我有 `sandbox_execute_code` 工具可以执行代码"，但它不知道"执行什么代码、按什么步骤执行，才是处理 PDF 的正确姿势"。

Skills 就是为了让 Agent 不仅能用工具，还能按说明书使用工具。本质是：给 LLM 读的结构化操作手册。

> Claude Code 这样强大的AI工具，底层工具就只有四个，读文件、写文件、编辑文件、执行命令行

背后的哲学叫做：“Bash is All You Need"，不需要提前把所有能力封装成 API，只要给 Agent 提供 `bash` 执行权，它就可以即兴写代码完成任何任务。

这也是 skills 和传统 MCP 工具最本质的区别：

- 传统 MCP 的思路。预先封装能力成 API -> Agent调用 -> 执行
- Skills + Bash 的思路。把"怎么做"写成操作手册 → Agent 按手册自己写代码 → `bash` 执行

skill 的优势在于灵活性，操作手册可以用自然语言描述"先检测文字层，再根据结果选择 pypdf 还是 OCR"这类业务判断逻辑，而 MCP 工具的 JSON Schema 里根本写不进去这种经验。代码不用预先封装好，遇到问题现场写，遇到 bug 现场调——这就是为什么 Skills 能让 Agent 处理任何 MCP 无法预先穷举的长尾场景。

Skill 按照执行方式分为两类：

- reference 参考型。特征：只有说明文档，无需代码执行。执行方式：注入主Agent上下文。场景：品牌规范、写作风格指南、产品知识库
- task任务型。特征：有操作步骤+执行脚步。执行方式：触发独立 Sub-Crew + 沙盒执行。场景：PDF解析、Word生成、数据处理

Agent 管理大量 skill 的方式是“渐进式披露"。主Agent只会读 skill 的 name+sescript。当主 Agent 决定要用某个 skill 时，才读取 skill 的完整正文。

每家企业都积累了大量私域知识——内部系统的操作规范、业务流程的最佳路径、行业经验的隐性知识。skill 可以迫使我们建设一个企业AI知识共享生态。知识不再锁在个人脑子里，而是以 skills 的形式沉淀、流通、进化。

MCP 的不可替代之处：权限认证与安全隔离、安全合规与审计追踪、外部系统集成基础设施。

最佳实践：

- skill 尽量保证职责单一，否则Agent 不知道调那个？只能随机使用一个。
- 外部的 skill 一定要 review，否则会有风险
- skill 超过 500 行时要做拆分。Anthropic 测试发现 超过 500 行的 skill.md 存在注意力衰减。注意要按照类型拆分独立 skill，每个保持 200 行以内
- 引用链不要超过一层。Claude 的 Skill 执行模式默认只读取 SKILL.md 本身和第一层直接引用文件（且通常只读前 100 行）。第三层文件永远不会被完整读取，等于白写
- 能沉淀成 script 的，少让模型动态生成代码。凡是有固定步骤的操作（PDF 文字层检测、DOCX XML 解包、数据清洗逻辑），优先写进 `scripts/` 目录的预制脚本，SKILL.md 指令直接调用脚本路径（`python /mnt/skills/pdf/scripts/extract.py`）。让 LLM 动态生成代码有三个隐患：每次生成结果不稳定、tokens 消耗大、无法做代码 Review。预制脚本是稳定锚点：测试一次通过，百次调用行为一致，还可以进 Git 被版本管理。
- skill 作为说明书，MCP做工具。将知识层与能力层分离。设计时严格划清职责：MCP Server 只暴露原子能力（执行 bash、读写文件、调用 API），Skill 负责把这些能力组合成"有意图的操作序列"。不要在 MCP 工具里嵌入业务逻辑，也不要在 SKILL.md 里定义新的工具 API。这样的好处是：换一套沙盒只需改 MCP Server 配置，换一套操作规范只需改 SKILL.md，两层各自演化，互不影响。这是软件工程里"关注点分离"原则在 AI 系统中的体现。

skill 管理四要素：命名规范、Review流程、版本管理、使用统计。

* **命名规范** ：`{动词}-{名词}` 格式，小写连字符，如 `parse-pdf`、`generate-report`；禁止用通用词（`process`、`handle`、`manage`）作为 Skill 名，语义模糊会导致主 Agent 路由混乱
* **Review 流程** ：新 Skill 提 PR，至少一名工程师 Review 业务逻辑，一名安全工程师 Review `scripts/` 的权限边界
* **版本管理** ：`load_skills.yaml` 进 Git，每次修改走 PR，生产环境总能回滚；在 `enabled: false` 下线而非直接删除，保留历史
* **使用统计** ：在 `_execute_skill_async` 里埋点，记录调用次数、成功率、平均耗时；超过 30 天未调用的 Skill 标记为"待废弃"，定期清理僵尸 Skill
