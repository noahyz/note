## 一、基础概念

### 1.1 帧（Frame）

视频的最小组成单位，每一帧代表一幅静止的图像。视频本质上是一组按时间顺序排列的图片序列，以足够快的速度连续播放，利用人眼的视觉暂留效应产生运动的错觉。

人眼生理结构决定：**帧率高于 16fps 时，画面即感觉连续**；超过 24fps 后，流畅感提升趋于平缓。

### 1.2 帧率（Frame Rate / FPS）

每秒显示的图片帧数，单位为 fps（frames per second）。

| 帧率 | 典型场景 |
|------|----------|
| 24fps | 电影标准，胶片感 |
| 30fps | 普通视频、电视 |
| 60fps | 游戏录制、运动视频 |
| 120fps / 240fps | 慢动作、高帧率直播 |

- 帧率越高，画面越流畅，但数据量成倍增加
- 帧率越低，画面有跳跃感

### 1.3 分辨率（Resolution）

图像的长度×宽度，即像素点总数，决定画面清晰度。

| 名称 | 分辨率 | 备注 |
|------|--------|------|
| SD（标清） | 720×480 | 早期电视标准 |
| HD（高清） | 1280×720 | 720p |
| Full HD（全高清） | 1920×1080 | 1080p，当前主流 |
| 2K | 2560×1440 | QHD |
| 4K（超高清） | 3840×2160 | UHD，流媒体主流趋势 |
| 8K | 7680×4320 | 广播级别 |

### 1.4 码率（Bit Rate）

单位时间内传输或处理的比特数，单位 bps/kbps/Mbps，直接决定视频文件大小与传输带宽需求。

**原始数据量估算公式：**

```
原始视频码率 = 帧率 × 分辨率 × 颜色位深
例：1080p/30fps/YUV420 的原始码率 ≈ 1920×1080×30×12bit ≈ 746 Mbps
```

经过压缩编码后，H.264 可将 1080p/30fps 压缩到 3～8 Mbps，压缩比超过 100:1。

**压缩比** = 原始数据量 / 压缩后码率。同一视频源、同一编码算法下：压缩比越高，画面质量越差。

### 1.5 GOP（Group of Pictures，画面组）

一组连续画面的集合，由 I 帧、P 帧、B 帧组成。

| 帧类型 | 全称 | 含义 | 特点 |
|--------|------|------|------|
| **I 帧** | 关键帧（Intra-coded frame） | 完整的独立图像 | 无需参考其他帧即可解码，体积最大 |
| **P 帧** | 前向预测帧（Predicted frame） | 相对前一帧的差别数据 | 依赖前一 I/P 帧，体积约为 I 帧的 1/3 |
| **B 帧** | 双向预测帧（Bi-directional frame） | 参考前后帧的差别数据 | 压缩率最高，约为 I 帧的 1/6，但解码延迟高 |

**GOP 对直播的影响：**

- 用户首次进入直播，播放器必须找到最近的 I 帧才能开始解码
- **GOP Cache（关键帧缓存）**：服务器缓存最近一个 GOP，新用户可立即获取关键帧，减少首帧等待
- GOP 越长：每个 I 帧间压缩效率更高（体积更小），但延迟更大、弱网容错性更差
- 直播场景一般设置 GOP 为 1～2 秒

### 1.6 帧内压缩与帧间压缩

| 压缩类型 | 说明 | 特点 |
|----------|------|------|
| **帧内压缩**（Spatial Compression） | 只考虑当前帧内像素间的冗余 | 有损压缩，I 帧使用 |
| **帧间压缩**（Temporal Compression） | 利用相邻帧之间时间上的冗余 | 高效压缩，P/B 帧使用 |

### 1.7 码率控制模式

| 模式 | 全称 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|------|----------|
| **CBR** | 固定码率 | 整个视频码率恒定 | 带宽可预测，存储简单 | 复杂场景质量差，简单场景浪费 | 直播推流、视频会议 |
| **VBR** | 可变码率 | 根据复杂度动态调整 | 质量均衡，整体最优 | 码率峰值不确定，不利于实时流 | 本地录制、点播存储 |
| **ABR** | 平均码率 | 在目标平均码率下可变 | 兼顾 CBR 和 VBR 优点 | 实现复杂 | 通用场景推荐 |
| **CRF** | 恒定质量因子 | 以视觉质量为目标 | 质量最均衡 | 文件大小不可控 | 离线转码、归档 |

## 二、流媒体技术栈四层架构

流媒体系统可以分为四层，从下到上依次是：

```
┌─────────────────────────────────────┐
│    编码层（Codec Layer）             │
│    H.264 / H.265 / AV1 压缩视频帧   │
│    AAC / Opus 压缩音频帧             │
├─────────────────────────────────────┤
│    封装层（Mux Layer）               │
│    FLV / TS / MP4 打包编码数据       │
├─────────────────────────────────────┤
│    协议层（Protocol Layer）          │
│    RTMP / HLS / WebRTC 规定如何传输  │
├─────────────────────────────────────┤
│    网络层（Network Layer）           │
│    TCP / UDP Socket 实际收发数据     │
└─────────────────────────────────────┘
```

这四层的关系类比：
- **编码层** = 内容本身（说什么）
- **封装层** = 包装盒子（怎么装）
- **协议层** = 快递规则（怎么发）
- **网络层** = 道路交通（通过哪条路）

## 三、音视频原始数据格式

采集到的未压缩原始音视频数据体积极大，必须经过编码压缩后才能传输存储。

### 3.1 视频原始数据：YUV

**YUV** 是视频领域最常用的颜色空间，将亮度（Y）与色度（UV）分离。相比 RGB，YUV 的优势在于：

- 利用人眼对亮度敏感、对色度不敏感的特点，对色度进行降采样
- 在相同视觉质量下，数据量比 RGB 更小
- 历史兼容性强（来自早期黑白/彩色电视）

> **概念说明：** YUV、Y'UV、YCbCr 是同一类技术的不同命名。严格来说，数字视频（MPEG、JPEG）中用的是 **YCbCr**，其中 Y 表示亮度（luma），Cb/Cr 表示蓝色/红色差值（chroma）。日常简称 YUV。

#### YUV 采样格式对比

| 采样格式 | 描述 | 数据量（4像素） | 适用场景 |
|----------|------|----------------|----------|
| **YUV 4:4:4** | 每个像素完整 YUV | 12 字节 | 专业视频制作 |
| **YUV 4:2:2** | 水平方向色度减半 | 8 字节 | 广播级视频 |
| **YUV 4:2:0** | 水平和垂直均减半 | 6 字节 | **最常用**，手机/互联网视频 |

#### YUV 存储方式

| 格式 | 存储方式 | 说明 |
|------|----------|------|
| **YUV420P**（I420） | Planar，Y/U/V 分平面存储 | 最常用，FFmpeg 默认 |
| **YUV420SP**（NV12/NV21） | Semi-planar，Y 独立，UV 交错 | Android 常用（NV21）、iOS 常用（NV12） |
| Packed（YUYV） | Y/U/V 交错连续存储 | 部分采集设备输出 |

### 3.2 视频原始数据：RGB

RGB 是显示器、摄像头输出的原始色彩空间，每个像素由 R（红）、G（绿）、B（蓝）三通道组成。

- **RGB24**：每通道 8bit，共 24bit/像素，最常见
- **RGBA32**：额外含 Alpha 透明通道，32bit/像素
- 采集到 RGB 后，通常先转换为 YUV 再进行编码

**RGB ↔ YUV 转换**是音视频处理中的常见操作，由 FFmpeg 的 `libswscale` 库负责。

### 3.3 音频原始数据：PCM

**PCM（Pulse Code Modulation，脉冲编码调制）**是音频的原始数字格式，将模拟声波采样、量化、编码成数字信号。

#### 关键参数

| 参数 | 说明 | 常见值 |
|------|------|--------|
| **采样率**（Sample Rate） | 每秒采集的采样点数 | 8kHz（电话）、44.1kHz（CD）、48kHz（视频） |
| **位深**（Bit Depth） | 每个采样点的精度 | 8bit（通话）、16bit（媒体主流）、24bit（专业） |
| **声道数**（Channels） | 单声道/立体声/多声道 | 1（Mono）、2（Stereo）、5.1、7.1 |

#### 数据量计算

```
原始音频码率 = 采样率 × 位深 × 声道数
例：48kHz × 16bit × 2ch = 1536 kbps（约 1.5Mbps）
```

**PCM 变体：**
- **PCM16**：signed short，-32768～32767，小端字节序，双声道时左右声道交替存储
- **浮点 PCM（float32）**：-1.0～1.0，专业音频处理常用

## 四、视频编码技术

视频编码的目标：**在尽可能小的数据量下，保持尽可能高的视觉质量。**

### 4.1 视频编码 vs 封装格式

> 类比：编码标准 = 编程语言，封装格式 = 工程项目文件
> 同一封装格式（如 MP4）可以容纳不同编码（H.264、H.265、AV1）

**最影响画质的是编码标准，而非封装格式。**

### 4.2 主流视频编码标准全面对比

#### H.264 / AVC（Advanced Video Coding）

- **发布时间：** 2003 年，由 ITU-T 与 MPEG 联合制定
- **原理：** 帧内预测 + 帧间预测 + 变换量化 + 熵编码，引入更灵活的宏块分割
- **压缩效率：** 相比 MPEG-2 提升约 50%
- **优势：** 
  - 兼容性最好，几乎所有设备、平台、浏览器、CDN 都支持
  - 编解码器成熟，各平台硬件加速普及
  - 技术社区丰富，工具链完善
- **劣势：** 
  - 压缩效率相比新一代标准低 30～50%
  - 同码率下画质不如 H.265/AV1
- **适用场景：** 直播推流、点播存储、监控录像、需要最大兼容性的场景

#### H.265 / HEVC（High Efficiency Video Coding）

- **发布时间：** 2013 年，H.264 的继任者
- **原理：** 引入更大的编码单元（CTU，最大 64×64）、更精细的帧内/帧间预测、并行处理优化
- **压缩效率：** 相比 H.264 提升约 50%，同等画质下码率降低一半
- **优势：**
  - 相同码率下画质显著更好（或相同画质更省带宽）
  - 支持 4K/8K 超高清
  - 主流设备已普遍支持硬件解码
- **劣势：**
  - 专利授权复杂，HEVC Advance、MPEG LA、Velos Media 三家授权池收费
  - 编码复杂度高，软件编码 CPU 消耗大
  - 部分老旧设备/浏览器不支持
- **适用场景：** 4K 点播、视频存储优化、OTT 流媒体、支持有限带宽的场景

#### VP9

- **发布时间：** 2013 年，Google 开发
- **压缩效率：** 与 H.265 相当
- **优势：**
  - 开源免专利费
  - YouTube 默认编码格式
  - Chrome、Firefox 等主流浏览器原生支持
- **劣势：**
  - 编码速度慢（有时比 H.264/H.265 更慢）
  - 硬件解码支持不如 H.264/H.265 普及
  - iOS/Safari 支持较晚
- **适用场景：** Web 视频、YouTube 平台、免版权费的互联网点播

#### AV1

- **发布时间：** 2018 年，由 Alliance for Open Media（AOMedia）开发，成员包括 Google、Netflix、Amazon、Apple 等
- **压缩效率：** 比 H.265 再提升约 30%，比 H.264 提升约 50%
- **优势：**
  - 完全免版权费、开源
  - 压缩效率最高，极大节省带宽
  - 浏览器支持快速增长（Chrome、Firefox 已支持，Safari 16.4+）
  - Netflix、YouTube 已大规模部署
- **劣势：**
  - 编码速度极慢（软件编码），对硬件依赖高
  - 硬件解码支持仍在普及阶段（2020 年后新设备基本支持）
  - 实时直播编码场景尚不成熟
- **适用场景：** 大规模点播（Netflix/YouTube）、低带宽优化、未来主流方向

#### H.266 / VVC（Versatile Video Coding）

- **发布时间：** 2020 年，最新一代标准
- **压缩效率：** 相比 H.265 再提升约 50%，相比 H.264 提升约 75%
- **优势：** 压缩率最高，专为 4K/8K/360° 视频、VR 设计
- **劣势：** 编码复杂度极高，硬件支持几乎为零，商业部署尚早
- **适用场景：** 下一代广播、8K 视频归档（未来）

#### MPEG 系列（历史）

| 标准 | 年份 | 主要改进 | 典型场景 |
|------|------|----------|----------|
| MPEG-1 | 1993 | 首个通用视频压缩标准 | VCD |
| MPEG-2 | 1995 | 支持高分辨率、场编码 | DVD、数字电视 |
| MPEG-4 Part 2 | 1999 | 对象编码 | 早期网络视频 |
| MPEG-4 AVC (H.264) | 2003 | 现代直播/点播基石 | — |

#### 编码标准综合对比表

| 标准 | 压缩效率（相对 H.264） | 专利费 | 硬件支持 | 编码速度 | 推荐场景 |
|------|----------------------|--------|----------|----------|----------|
| H.264 | 基准 | 有（已有免费期） | 极好 | 快 | 直播、通用兼容 |
| H.265 | +50% | 复杂/收费 | 好 | 中等 | 4K点播、存储优化 |
| VP9 | +50% | 免费 | 中 | 慢 | Web视频 |
| AV1 | +80% | 免费 | 增长中 | 极慢 | 大规模点播 |
| H.266 | +150% | 待定 | 几乎无 | 极慢 | 未来归档 |

## 五、音频编码技术

### 5.1 主流音频编码格式全面对比

#### MP3（MPEG-1 Audio Layer III）

- **标准化：** 1993 年，ISO MPEG-1 第三层
- **采样率：** 32/44.1/48 kHz（MPEG-1），最大立体声
- **推荐码率：** 128 kbps 及以上（立体声）
- **专利：** 2017 年后所有专利过期，完全免费
- **优势：** 兼容性最广，几乎所有设备和软件都支持
- **劣势：** 相同码率下音质不如 AAC/Opus；低比特率表现差
- **适用：** 音乐分发、音频存储、跨平台兼容

#### AAC（Advanced Audio Coding，高级音频编码）

- **标准化：** MPEG-2/MPEG-4，MP3 的官方继任者
- **采样率：** 8～192 kHz，支持最多 48 声道
- **推荐码率：** 96 kbps 及以上（立体声）
- **变体：**
  - **AAC-LC**（低复杂度）：最常用，兼容性好
  - **HE-AAC v1**（High Efficiency）：低码率下效果好，适合流媒体
  - **HE-AAC v2**：在 HE-AAC v1 基础上加入参数立体声，适合极低码率
  - **AAC-LD/ELD**（低延迟）：实时通信场景
- **专利：** 需向 Via Licensing 或 MPEG LA 授权（OEM 和软件商）
- **优势：** 相同码率下音质显著优于 MP3；苹果设备原生支持；AAC-LC 为直播标准
- **劣势：** 专利收费；低比特率不如 Opus
- **适用：** **直播音频首选（AAC-LC）**、iTunes、iOS/macOS、数字广播

#### Opus

- **标准化：** 2012 年，IETF RFC 6716，由 Skype（SILK）+ Xiph.org（CELT）合并
- **采样率：** 8/12/16/24/48 kHz
- **码率范围：** 6 kbps ～ 510 kbps
- **专利：** 完全免费开源
- **优势：**
  - 延迟极低（2.5ms ～ 60ms），是音频编解码器中延迟最低的之一
  - 低码率下音质超越 AAC 和 MP3
  - 同时适合语音和音乐（自适应模式切换）
  - WebRTC 强制要求实现 Opus
  - WhatsApp、Discord 等均使用 Opus
- **劣势：** 仅支持单声道/立体声，不支持多声道；部分旧设备不支持
- **适用：** **实时通话（WebRTC 标准）**、VoIP、视频会议、在线教育

#### AC-3 / Dolby Digital（杜比数字）

- **采样率：** 32/44.1/48 kHz
- **声道：** 最高 5.1 声道
- **升级版：** E-AC3（Dolby Digital Plus）支持 7.1 声道
- **专利：** AC-3 已过期免费；EAC3 需杜比授权
- **优势：** 环绕声支持好，院线/家庭影院标准；Apple 设备支持
- **劣势：** 商业授权费；不适合低延迟实时通信
- **适用：** 电影院、蓝光光盘、家庭影院、OTT 流媒体

#### FLAC（Free Lossless Audio Codec）

- 无损压缩，保留原始音频所有信息
- 压缩比约 50%（相比 PCM）
- 完全开源免费
- **适用：** 音乐存档、高保真音频、专业制作

#### WAV

- 无压缩原始 PCM 存储（RIFF 格式）
- 音质最原始，文件最大
- **适用：** 音频编辑中间格式、专业制作

#### WMA（Windows Media Audio）

- 微软开发的专有编解码器家族
- WMA Pro 支持最高 7.1 声道和 96 kHz
- **适用：** Windows 生态下的媒体播放

#### 音频编码综合对比

| 编解码器 | 类型 | 典型码率 | 延迟 | 免费 | 最大声道 | 适用场景 |
|---------|------|---------|------|------|---------|---------|
| MP3 | 有损 | 128～320 kbps | 高 | ✅ | 立体声 | 音乐分发 |
| AAC-LC | 有损 | 96～256 kbps | 中 | ❌ | 48ch | 直播/点播 |
| HE-AAC | 有损 | 32～128 kbps | 中 | ❌ | 多 | 低带宽流媒体 |
| Opus | 有损 | 6～510 kbps | **极低** | ✅ | 立体声 | 实时通话 |
| AC-3 | 有损 | 192～640 kbps | 高 | ❌ | 5.1 | 院线/影院 |
| FLAC | 无损 | ~1000 kbps | 高 | ✅ | 多 | 音乐存档 |
| PCM/WAV | 无压缩 | 1536 kbps+ | 无 | ✅ | 多 | 编辑中间格式 |

## 六、视频封装格式

封装格式（Container Format）是一种将视频流、音频流、字幕流及元数据按一定规则组织存储的"容器"。**封装格式决定怎么组织，不决定画质。**

### 6.1 FLV（Flash Video）

- **结构：** 流式结构，由多个 `PreviousTagSize + Tag` 顺序组成
- **特点：** 文件头固定小，音视频数据可随时追加到末尾，无需重写文件头
- **优势：**
  - 文件极小，加载速度快，适合网络传输
  - 流式写入，**非常适合直播录制**（可随时开播/关播）
  - 在线教育等场景中多个 FLV 片段可直接拼接
- **劣势：**
  - 依赖 Adobe Flash（已于 2020 年停止支持），浏览器端播放需特殊处理（flv.js）
  - 不支持 H.265、AV1 等新编码
  - 不适合点播随机seek（无索引）
- **适用：** 推流端封装、直播录制、HTTP-FLV 协议传输
- **支持编码：** H.264（视频）+ AAC/MP3（音频）

### 6.2 TS（MPEG-2 Transport Stream）

- **结构：** 固定 188 字节的包（Packet）组成，每包含有 PID 标识
- **优势：**
  - 流式封装，无需全局索引，首次载入延迟极小
  - **两个 TS 片段可以无缝拼接**，播放器连续播放
  - 容错性强，中途丢包不影响其他包解码
  - HLS 协议的底层格式
- **劣势：**
  - 包头开销较大（每 188 字节有固定包头）
  - 不适合本地点播存储（seek 效率低）
- **适用：** HLS 切片格式、广播电视流、直播传输

### 6.3 MP4（MPEG-4 Part 14）

- **结构：** 索引式（moov box），文件头包含完整的索引信息（位置、时长、大小）
- **优势：**
  - 兼容性最好，几乎所有设备和平台都支持
  - 支持快速 seek（通过索引精确定位）
  - 支持 H.264/H.265/AV1 等主流编码
  - 适合点播、存储、剪辑
- **劣势：**
  - moov box 默认在文件尾，如果网络播放未等全部下载完则无法播放（可通过 `moov` 前置 `faststart` 优化）
  - 录制过程中如意外中断，文件可能损坏（因索引未写完）
  - 不适合实时直播录制（文件头会随内容增长而变化）
- **适用：** 点播存储、视频剪辑、归档、跨平台分发

### 6.4 MKV（Matroska Video）

- 开源免费的容器格式，支持几乎所有视频/音频/字幕编码
- 支持多音轨、多字幕轨道，章节标记
- **优势：** 灵活性最强，无格式限制
- **劣势：** 部分设备和平台不支持，主要在 PC 端使用
- **适用：** 本地高清存储、多语言视频、字幕嵌入

### 6.5 WebM

- Google 开发的开放格式，基于 Matroska
- 专为 Web 设计，绑定 VP8/VP9/AV1 视频 + Vorbis/Opus 音频
- 完全免费
- **适用：** Chrome 等浏览器的 HTML5 视频

### 6.6 HLS 格式（m3u8 + TS）

- 严格说不是封装格式，而是协议定义的文件组合方式
- m3u8：索引文件（播放列表），描述切片顺序和地址
- ts：实际的媒体切片文件
- 详见[第七章传输协议部分](#732-hls)

### 6.7 封装格式综合对比

| 格式 | 结构类型 | 直播录制 | 点播seek | 流式传输 | 兼容性 | 推荐用途 |
|------|---------|---------|---------|---------|--------|---------|
| FLV | 流式 | ✅ 最佳 | ❌ | ✅ | 中（需flv.js） | 推流/录制 |
| TS | 流式 | ✅ | ❌ | ✅ | 好 | HLS切片 |
| MP4 | 索引式 | ❌ | ✅ 最佳 | 需优化 | 最好 | 点播/归档 |
| MKV | 索引式 | ❌ | ✅ | ❌ | 差（PC端） | 本地存储 |
| WebM | 索引式 | ❌ | ✅ | 中 | Web好 | Web视频 |

## 七、流媒体传输协议

传输协议决定"媒体数据如何在网络中流动"，是直播技术栈中差异最大、选型最关键的一环。

### 7.1 RTMP（Real Time Messaging Protocol）

- **全称：** 实时消息传输协议
- **开发者：** Adobe System（现已开源）
- **底层：** 基于 TCP，默认端口 1935
- **延迟：** 1～3 秒（典型值）

#### 工作原理

RTMP 将数据切分为固定大小的 chunk（块）进行传输，每个连接可以多路复用不同的逻辑通道（Channel）。数据包（Message）包括音频、视频和控制信息，经过切片后按序发送。

**RTMP 变种：**
| 变种 | 说明 |
|------|------|
| RTMP | 基础版，明文传输 |
| RTMPS | SSL/TLS 加密，安全传输 |
| RTMPT | 基于 HTTP 隧道，穿防火墙 |
| RTMPE | Adobe 私有加密 |
| RTMFP | 基于 UDP 的 P2P 变种（Flash） |

#### 优势
- 技术成熟，CDN 支持广泛
- 延迟相对 HLS 低得多
- 实现库丰富（librtmp、FFmpeg 内置）
- 推流协议的事实标准

#### 劣势
- iOS 不原生支持（需 flv.js 等辅助播放）
- Adobe 已停止更新（协议冻结）
- 不支持 H.265 等新编码
- 基于 TCP，弱网下丢包重传可能导致堆积卡顿

#### 适用场景
- **推流端到流媒体服务器（最佳选择）**
- 流媒体服务器内部分发
- 对延迟有要求但不需要极致实时的直播

---

### 7.2 HLS（HTTP Live Streaming）

- **全称：** HTTP 实时流传输
- **开发者：** Apple（2009 年提出）
- **底层：** 基于 HTTP，通过普通 Web 服务器分发
- **延迟：** 标准 HLS 10～30 秒；Low-Latency HLS（LL-HLS，2019年）可降至 2～5 秒

#### 工作原理

HLS 将媒体内容切割成若干小的 TS 片段（通常 2～10 秒一片），并生成 m3u8 播放列表文件：

```
#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:10
#EXTINF:9.9,
segment001.ts
#EXTINF:9.9,
segment002.ts
...
```

播放器根据时间戳定期请求 m3u8 文件，获取最新切片地址并下载播放。本质上是以点播技术实现直播。

```
video/
├── index.m3u8          # 索引文件，指向各档码率的 m3u8
├── 1080p.m3u8          # 高分档索引
│   ├── segment_000.ts  # 每个 ts 约 2~10 秒
│   ├── segment_001.ts
│   ├── segment_002.ts
│   └── ...
├── 720p.m3u8
│   ├── segment_000.ts
│   └── ...
└── 480p.m3u8
```

**自适应码率（ABR）：** HLS 支持多码率流（Master Playlist），播放器根据网络状况自动切换到最合适的码率。

#### 优势
- 天然穿透防火墙（HTTP 80/443 端口）
- iOS/Safari 原生支持
- 浏览器无需插件，HTML5 video 标签直接播放
- 自动码率自适应
- CDN 分发压力小（普通 HTTP 静态文件）
- 可在任何标准 Web 服务器上部署

#### 劣势
- 延迟大（标准 HLS 20～30 秒）
- 大量 TS 小文件增加存储和 IO 压力
- 每次请求需要 HTTP 三次握手（短连接开销）

#### Low-Latency HLS（LL-HLS）
Apple 于 2019 年发布，通过以下手段将延迟降至 2～5 秒：
- 切片时长缩短至 200ms～500ms
- 使用 HTTP/2 服务器推送预推切片
- Delta Playlist Update 增量更新播放列表

#### 适用场景
- **移动端播放（iOS 必须使用）**
- 跨平台浏览器播放
- 对延迟要求不高的直播（新闻、体育回放）
- 点播系统

---

### 7.3 HTTP-FLV

- **底层：** HTTP 长连接 + FLV 流式封装
- **延迟：** 1～3 秒，与 RTMP 相当甚至更低
- **原理：** 服务器建立一个 HTTP 长连接，将 FLV 数据持续推送给客户端

#### 与 RTMP 对比

| 对比项 | RTMP | HTTP-FLV |
|--------|------|----------|
| 底层协议 | TCP（私有协议） | HTTP |
| 防火墙穿透 | 差（1935 端口经常被封） | 好（80/443 端口） |
| 延迟 | 1～3 秒 | 1～3 秒（略低） |
| CDN 支持 | 需专用 RTMP 节点 | 普通 HTTP CDN 即可 |
| 浏览器兼容 | 需 Flash 或 flv.js | 需 flv.js |
| 协议复杂度 | 较高 | 低 |

#### 适用场景
- PC 端 Web 直播播放（配合 flv.js）
- 需要穿透企业防火墙的场景
- 对延迟要求较高但不需要 WebRTC 级别实时的场景

---

### 7.4 WebRTC（Web Real-Time Communication）

- **全称：** 网页实时通信
- **开发者：** Google 主导，W3C/IETF 标准化
- **底层：** 通常基于 UDP（DTLS-SRTP）
- **延迟：** **< 500 毫秒，典型值 100～300 毫秒**

#### 技术架构

WebRTC 是一套完整的实时通信框架，涉及多个协议协同工作：

```
Web App (JavaScript API)
    ↓
信令服务器（Signaling Server）—— 协商 SDP/ICE Candidate
    ↓
ICE 框架
  ├── STUN（NAT 穿透，获取公网地址）
  └── TURN（中继服务器，NAT 穿透失败时的备选）
    ↓
DTLS（握手，密钥交换）
    ↓
SRTP/SRTCP（加密音视频数据传输）
```

**关键组件：**

| 组件 | 作用 |
|------|------|
| **SDP**（Session Description Protocol） | 描述媒体能力（编码、分辨率、带宽等），用于 Offer/Answer 协商 |
| **ICE**（Interactive Connectivity Establishment） | P2P 连接建立框架，整合 STUN 和 TURN |
| **STUN** | 帮助客户端发现自己的公网 IP 和端口（NAT 穿透） |
| **TURN** | 当直接 P2P 不通时，通过中继服务器转发（保底方案） |
| **DTLS** | 基于 UDP 的 TLS，负责密钥协商 |
| **SRTP** | 加密的 RTP，传输音视频数据 |
| **SRTCP** | 加密的 RTCP，传输质量统计/控制信息 |

#### 优势
- **延迟最低**（< 1 秒，适合实时互动）
- 内置加密（DTLS + SRTP），安全性高
- 内置 NAT 穿透能力
- 内置带宽自适应和丢包恢复（NACK、FEC）
- 浏览器原生支持，无需插件
- 完全开源免费（Google 开源）

#### 劣势
- P2P 架构下大规模分发困难（需要 SFU/MCU）
- 服务器架构设计复杂（信令服务器 + TURN 服务器）
- 跨设备兼容性问题（回声消除、设备差异）
- 无法直接接入传统 CDN，需要专门的 WebRTC CDN 或媒体服务器转换
- 高并发时服务器压力大

#### 适用场景
- **实时互动直播**（主播与观众连麦）
- 视频会议、在线教育
- 1对1音视频通话
- 低延迟游戏直播互动场景

---

### 7.5 SRT（Secure Reliable Transport）

- **全称：** 安全可靠传输
- **开发者：** Haivision 开发，2017 年开源
- **底层：** 基于 UDP，加入 ARQ（自动重传请求）和 FEC（前向纠错）
- **延迟：** 120ms ～ 2 秒（可配置，弱网下自动调整）

#### 核心机制
- **ARQ 重传：** 接收端检测丢包，发送 NAK 请求重传
- **FEC：** 发送端额外发送纠错包，接收端可在不重传的情况下恢复丢失数据
- **加密：** 内置 AES-128/256 加密
- **多路径：** 支持 Bonding（多网络接口聚合，提升可靠性）

#### 与 RTMP 对比

| 对比项 | RTMP | SRT |
|--------|------|-----|
| 底层 | TCP | UDP + ARQ |
| 弱网表现 | 差（TCP 重传队头阻塞） | 好（选择性重传） |
| 加密 | 需外层 TLS | 内置 AES |
| 延迟 | 1～3 秒 | 120ms～2 秒 |
| CDN 支持 | 广泛 | 增长中 |
| 适用 | 稳定局域网/CDN推流 | 跨公网远程推流 |

#### 适用场景
- **远程制作（Remote Production）**，如演播室到广播中心的传输
- 跨公网的不稳定链路推流
- 广播级视频传输
- 体育赛事现场直播的信号回传

---

### 7.6 RTSP（Real Time Streaming Protocol）

- **定位：** 流媒体控制协议（不直接传输数据）
- **搭档：** 通常与 RTP（数据传输）+ RTCP（质量反馈）配合使用
- **底层：** TCP 或 UDP
- **延迟：** 低（100～500ms，取决于实现）

#### 与 RTP/RTCP 的关系
```
RTSP —— 控制（PLAY/PAUSE/SETUP 等命令，类似 HTTP）
 ↓
RTP  —— 数据传输（实时传输音视频包）
 ↓
RTCP —— 质量控制（丢包率、延迟统计、QoS 反馈）
```

#### 适用场景
- **IP 摄像头/视频监控系统**（ONVIF 协议基于 RTSP）
- NVR、DVR 等安防设备
- 闭路电视（CCTV）网络化改造
- 需要精确播放控制（快进/暂停/跳转）的场景

---

### 7.7 DASH（Dynamic Adaptive Streaming over HTTP）

- **全称：** 基于 HTTP 的动态自适应流
- **标准化：** MPEG-DASH，2012 年 ISO 标准
- **原理：** 与 HLS 类似，将视频切片，通过 MPD（Media Presentation Description）文件描述
- **格式：** 切片通常为 MP4 fMP4（fragmented MP4），也支持 TS
- **延迟：** 标准 DASH 10～30 秒；Low-Latency DASH（CMAF）可降至 3～5 秒
- **特点：** 
  - 开放标准，不依赖特定厂商
  - 支持 DRM（数字版权保护）
  - YouTube 使用 DASH
- **适用：** 点播平台、需要 DRM 保护的内容

```
video/
├── manifest.mpd        # 描述文件
├── video_1080p/
│   ├── chunk_0.m4s
│   ├── chunk_1.m4s
│   └── ...
├── video_720p/
└── audio/
    ├── chunk_0.m4s
    └── ...
```

---

### 7.8 QUIC / WebTransport（新兴）

- **QUIC：** Google 开发，HTTP/3 的底层协议，基于 UDP + 多路复用 + 0-RTT 握手
- **WebTransport：** 基于 QUIC 的 Web API，可替代 WebSocket 用于实时媒体传输
- **MoQ（Media over QUIC）：** IETF 在 2023 年开始标准化，旨在替代 RTMP 成为下一代推流协议
- **现状：** 仍在标准化阶段，尚未大规模商用

---

### 7.9 传输协议综合对比

| 协议 | 底层 | 延迟 | 穿防火墙 | 兼容性 | 加密 | 适合推流 | 适合播放 |
|------|------|------|---------|--------|------|---------|---------|
| RTMP | TCP | 1～3s | 差 | 好 | 需外层 | ✅ 主流 | ❌ |
| HLS | HTTP | 10～30s | ✅ | 最好 | HTTPS | ❌ | ✅ iOS必须 |
| LL-HLS | HTTP | 2～5s | ✅ | 好 | HTTPS | ❌ | ✅ |
| HTTP-FLV | HTTP | 1～3s | ✅ | 好 | HTTPS | ❌ | ✅ Web |
| RTSP+RTP | TCP/UDP | <1s | 差 | 中 | 无 | ✅ 监控 | ✅ 监控 |
| WebRTC | UDP | <500ms | ✅ | 好 | 强制 | ✅ 互动 | ✅ 互动 |
| SRT | UDP | 120ms～2s | 好 | 增长 | 内置 | ✅ 跨网推流 | ❌ |
| DASH | HTTP | 10～30s | ✅ | 好 | HTTPS | ❌ | ✅ 点播 |

## 八、直播完整链路

一个完整的直播系统，从主播到观众，完整链路为：

```
主播端
  ├── 1. 采集（摄像头/麦克风）
  ├── 2. 前处理（美颜/水印/混音）
  ├── 3. 编码（H.264 + AAC）
  └── 4. 推流（RTMP → 流媒体服务器）

服务端
  ├── 5. 接收推流（源站）
  ├── 6. 转码（多码率）/ 录制 / 截图 / 鉴黄
  └── 7. CDN 分发（边缘节点缓存）

观众端
  ├── 8. 拉流（HLS/HTTP-FLV/RTMP）
  ├── 9. 解封装（Demux）
  ├── 10. 解码（软解/硬解）
  └── 11. 渲染播放 + 互动（弹幕/礼物/聊天）
```

## 九、视频采集

### 9.1 硬件层

| 硬件 | 功能 |
|------|------|
| **CCD / CMOS 图像传感器** | 将光信号转换为电信号（视频采集核心芯片） |
| **麦克风 / 拾音器** | 将声波转换为电信号（音频采集核心） |
| **ADC（模数转换器）** | 将模拟电信号转换为数字 PCM 数据 |

- 视频采样输出：YUV 或 RGB 格式的原始帧数据
- 音频采样输出：PCM 格式的原始采样数据

### 9.2 iOS 平台采集：AVFoundation

苹果官方的音视频框架，提供 Objective-C/Swift 接口。

**核心类：**

| 类 | 作用 |
|----|------|
| `AVCaptureSession` | 协调所有输入输出，是整个采集流程的中枢 |
| `AVCaptureDevice` | 代表物理设备（摄像头、麦克风），可配置焦点/白平衡等 |
| `AVCaptureDeviceInput` | 将设备包装为输入源 |
| `AVCaptureVideoDataOutput` | 视频数据输出，通过 SampleBufferDelegate 回调每帧数据 |
| `AVCaptureAudioDataOutput` | 音频数据输出 |
| `AVCaptureVideoPreviewLayer` | 实时预览图层 |

**采集流程（8 步）：**

```
1. 创建 AVCaptureSession
2. 获取摄像头/麦克风设备
3. 创建输入对象（AVCaptureDeviceInput）
4. 创建视频输出（AVCaptureVideoDataOutput）
5. 创建音频输出（AVCaptureAudioDataOutput）
6. 将输入/输出添加到 Session（自动建立连接）
7. 创建预览图层并添加到 UI
8. 启动 Session
```

### 9.3 Android 平台采集：Camera2 API

Android 5.0 引入 Camera2，提供更精细的曝光、对焦、白平衡控制，支持 RAW 格式和高速摄像。

### 9.4 Web 平台采集：getUserMedia

WebRTC 的 `getUserMedia()` API 直接访问浏览器摄像头和麦克风，返回 MediaStream。

### 9.5 额外功能

**切换摄像头：** 从 Session 中移除当前摄像头输入，添加新方向的摄像头输入。

**聚焦控制：** 将屏幕触摸坐标通过 `AVCaptureVideoPreviewLayer` 转换为摄像头坐标系，设置自动对焦点。

**曝光控制：** 同步设置曝光点，防止逆光场景出现过曝/欠曝。

## 十、视频处理与美颜

### 10.1 视频处理原理

视频帧数据在 GPU 上逐帧渲染，利用 GPU 并行处理能力对像素进行变换。

基本流程：
```
采集原始帧 → 上传 GPU → Shader 滤镜处理 → 输出处理后帧 → 编码
```

### 10.2 美颜核心算法

| 效果 | 算法 | 说明 |
|------|------|------|
| **磨皮** | 双边滤波（Bilateral Filter） | 有针对性地模糊像素，**保留边缘清晰度**，不同于简单高斯模糊会模糊边缘 |
| **美白** | 亮度提升（Brightness Filter） | 提高图像整体亮度分量（YUV 中的 Y 值） |
| **红润** | 颜色曲线调整（Color Curve） | 增强红色通道分量 |
| **大眼/瘦脸** | 面部关键点检测 + 仿射变换 | 需要 AI 人脸检测（Face Landmark） |
| **滤镜特效** | LUT（Look Up Table，颜色查找表） | 通过 3D LUT 贴图进行颜色映射 |

**双边滤波**对比高斯模糊：

| 算法 | 边缘处理 | 计算量 |
|------|---------|--------|
| 高斯模糊（Gaussian Blur） | 模糊（不区分边缘） | 低 |
| 双边滤波（Bilateral Filter） | 保留边缘 | 高 |

### 10.3 GPUImage 框架

基于 OpenGL ES 2.0 的开源 iOS 图像/视频处理框架（Objective-C），内置 120+ 种滤镜。

**GPUImage 处理链（链式调用）：**

```
Source（GPUImageVideoCamera）
    ↓ addTarget
Filter（GPUImageBilateralFilter）  ← 磨皮
    ↓ addTarget
Filter（GPUImageBrightnessFilter） ← 美白
    ↓ addTarget
Final Target（GPUImageView）      ← 渲染到屏幕
```

**主要组件：**

| 组件类型 | 代表类 | 说明 |
|---------|--------|------|
| Source（源） | GPUImageVideoCamera | 实时视频源 |
| Source（源） | GPUImagePicture | 静态图片源 |
| Filter（滤镜） | GPUImageFilter 及子类 | 各种处理算法 |
| Final Target | GPUImageView | 显示到屏幕 |
| Final Target | GPUImageMovieWriter | 写入视频文件 |

### 10.4 GPUPixel（新一代跨平台方案）

- 支持 iOS、Android、Web（WASM）、macOS、Windows 全平台
- 支持实时视频流处理（适用于 WebRTC/RTMP 场景）
- 提供完整美颜：磨皮、美白、瘦脸、大眼、腮红、口红等

### 10.5 OpenGL 与 OpenGL ES

| 框架 | 全称 | 平台 | 说明 |
|------|------|------|------|
| OpenGL | Open Graphics Library | 桌面端 | 跨平台 2D/3D 图形 API |
| OpenGL ES | OpenGL for Embedded Systems | 移动端 | OpenGL 子集，针对移动设备优化 |
| Metal | — | Apple 平台 | Apple 自研图形 API，比 OpenGL ES 性能更好 |
| Vulkan | — | Android/桌面 | 低层级高性能图形 API |

## 十一、编解码实现方案

### 11.1 软编码 vs 硬编码

| 对比项 | 软编码（Software Encoding） | 硬编码（Hardware Encoding） |
|--------|---------------------------|---------------------------|
| **实现方式** | 纯 CPU 运算 | GPU/DSP/FPGA/ASIC 专用芯片 |
| **兼容性** | 最好（纯软件无硬件限制） | 依赖硬件支持，不同设备可能不同 |
| **编码速度** | 相对慢 | 快（专用硬件加速） |
| **画质** | 更好（算法灵活，可充分优化） | 略差（算法固化，优化有限） |
| **CPU 占用** | 高（主要消耗 CPU） | 低（解放 CPU） |
| **功耗** | 高 | 低 |
| **代表** | x264/x265/FFmpeg 软编 | VideoToolbox/MediaCodec/NVENC |

**结论：** 直播场景推荐优先使用硬编码（低延迟、低功耗），对画质要求极高的离线转码使用软编码。

### 11.2 主要编解码框架

#### FFmpeg

- **定位：** 跨平台开源音视频处理框架，支持几乎所有格式
- **许可证：** LGPL / GPL（视配置而定）
- **核心库：**

| 库 | 功能 |
|----|------|
| `libavcodec` | 编解码器（H.264/H.265/AAC 等） |
| `libavformat` | 封装/解封装（MP4/FLV/TS 等） |
| `libavfilter` | 滤镜（裁剪、缩放、叠加等） |
| `libswscale` | 图像缩放、色彩空间转换（YUV ↔ RGB） |
| `libswresample` | 音频重采样、声道混合、格式转换 |
| `libavutil` | 工具函数（哈希、数学、随机数） |
| `libpostproc` | 视频后处理 |

#### x264 / x265

- x264：高质量 H.264 开源编码器
- x265：高质量 H.265 开源编码器
- 两者都是 FFmpeg 的软件编码后端

#### VideoToolbox（iOS/macOS 硬编）

- Apple 官方硬件编解码 API，iOS 8+ 开放
- 支持 H.264、H.265 的硬件编码和解码
- 编码速度快，功耗低

#### MediaCodec（Android 硬编）

- Android 4.1+ 引入的硬件编解码 API
- 支持 H.264、H.265、VP8、VP9、AV1（新设备）
- 兼容性问题较多（不同厂商实现差异大）

#### NVENC / NVDEC（NVIDIA GPU 编解码）

- NVIDIA 显卡的硬件编解码 API
- 编码速度极快，适合服务器端实时转码

#### fdk-aac

- AAC 音频编解码库（来自 Fraunhofer）
- 音质优于 FFmpeg 内置 AAC 编码器

### 11.3 硬解码 vs 软解码

| 对比项 | 硬解码 | 软解码 |
|--------|--------|--------|
| 设备 | GPU 解码 | CPU 解码 |
| 播放流畅度 | 好（省 CPU，专用加速） | 差（高 CPU 占用） |
| 兼容性 | 差（部分格式无硬件支持） | 好（软件实现灵活） |
| 功耗 | 低 | 高 |
| 典型代表 | VideoToolbox、MediaCodec | FFmpeg 软解 |

## 十二、推流与拉流

### 12.1 推流（Streaming / Publish）

推流是将本地采集、编码后的音视频数据，通过网络协议上传到流媒体服务器的过程。

**推流协议选择：**
- **RTMP：** 最常用的推流协议，CDN 支持最广泛
- **SRT：** 跨公网、弱网环境首选
- **WebRTC：** 需要与观众实时互动的场景

**推流参数关键配置：**
- 视频码率：直播通常 1～8 Mbps（依据分辨率）
- 音频码率：AAC 128 kbps
- GOP：1～2 秒（保证秒开）
- 关键帧间隔 = GOP 大小

### 12.2 拉流（Pull Streaming / Play）

观众端从流媒体服务器获取视频流的过程。

**拉流协议选择原则：**

| 需求 | 推荐协议 |
|------|---------|
| iOS 原生播放 | HLS（必须） |
| Android 通用 | HLS 或 HTTP-FLV |
| PC Web 播放 | HTTP-FLV（flv.js）或 HLS |
| 实时互动（< 1s 延迟） | WebRTC |
| 安防监控 | RTSP |
| 追求低延迟 | HTTP-FLV 或 WebRTC |

### 12.3 解封装（Demuxing）

接收到的数据流（如 FLV、TS）需要先解封装，将音频流和视频流分离，再分别送入各自的解码器。

```
输入流（FLV/TS）
    ↓ Demux（解封装）
  ├── 视频包（H.264/H.265） → 视频解码器 → YUV → 渲染
  └── 音频包（AAC/Opus）   → 音频解码器 → PCM → 播放
```

### 12.4 音视频同步（AV Sync）

- 音频和视频来自两个独立的解码通道，必须同步播放
- 通常以**音频时钟为基准**，视频帧根据 PTS（Presentation Timestamp）与音频对齐
- 若视频超前：等待；若视频落后：丢帧追赶

## 十四、CDN 内容分发网络

### 14.1 CDN 概念

**CDN（Content Delivery Network，内容分发网络）** 通过在全球部署大量边缘节点（Edge Node），将内容缓存到离用户最近的节点，以实现快速访问、减少骨干网压力。

### 14.2 CDN 架构

```
                     ┌────────────────────────────────┐
   主播              │          源站服务器              │
   推流 ────────────→│  (Origin Server / 流媒体服务器)  │
                     └─────────────┬──────────────────┘
                                   │ 分发
                     ┌─────────────▼──────────────────┐
                     │         CDN 边缘节点             │
                     │  (北京节点) (上海节点) (广州节点) │
                     └─────────────┬──────────────────┘
                                   │ 就近访问
                     ┌─────────────▼──────────────────┐
                     │            观众                  │
                     └────────────────────────────────┘
```

### 14.3 CDN 工作流程

1. 主播将流推送到源站服务器
2. CDN 边缘节点检测到流请求，若本节点无缓存，向上一级节点（或源站）**回源**请求
3. 源站将流分发到边缘节点并缓存
4. 观众请求就近 CDN 边缘节点获取流
5. 边缘节点直接响应观众，无需每次回源

### 14.4 关键概念

| 概念 | 说明 |
|------|------|
| **回源（Back-to-Origin）** | 边缘节点无缓存时，向父节点或源站请求内容 |
| **回源率** | 边缘节点需要回源的请求比例，越低越好（说明缓存命中率高） |
| **带宽峰值** | CDN 需要支撑的最大并发带宽 |
| **负载均衡** | 将用户请求分配到多台服务器，避免单点过载 |
| **QoS（Quality of Service）** | 带宽管理策略，保障不同优先级流量的传输质量 |
| **GSLB** | 全局负载均衡，跨数据中心的流量调度 |

### 14.5 直播 CDN 的特殊性

- 直播是"一对多"推送场景，CDN 边缘节点订阅源站流，再分发给多个观众
- 直播延迟受 GOP Cache 影响：新用户需要等到下一个 I 帧才能开始播放
- CDN 节点通常需要支持 RTMP 拉流（从源站）和 HLS/HTTP-FLV 推送（到观众）

## 十六、多方通信架构

多方音视频（如视频会议、连麦直播）需要特殊的服务器架构来处理多个媒体流。

### 16.1 Mesh（网状 P2P）

每个终端与其他所有终端建立直接 P2P 连接，形成全连接网状结构。

```
   A ←——→ B
   ↕ ×   ↕
   C ←——→ D
```

- **优点：** 无需服务器，延迟最低
- **缺点：** 每个终端的上行带宽需求随人数线性增长（N 个人需要上传 N-1 路流），人数超过 4 人即不实用
- **适用：** 1v1 通话、极少人数场景

### 16.2 MCU（Multipoint Conferencing Unit，多点会议单元）

所有终端将媒体流发送给服务器，服务器将所有流**混合（Mix）**后再发给每个终端。

```
A ──→
B ──→  [MCU 服务器] → 混合流 → 广播给所有人
C ──→
```

- **优点：** 客户端带宽需求固定（只需上传 1 路、下载 1 路混合流）
- **缺点：** 服务器压力极大（实时混流需要大量 CPU/GPU 资源）；混流引入延迟；灵活性差
- **适用：** 带宽受限的低端设备会议，MCU 服务器算力充足的场景

### 16.3 SFU（Selective Forwarding Unit，选择性转发单元）

所有终端发流给服务器，服务器选择性地转发每路流给对应的终端，**不做混流**。

```
A ──→
B ──→  [SFU 服务器] → A的流发给B、C；B的流发给A、C；...
C ──→
```

- **优点：** 服务器只转发，无需编解码，压力小；延迟低；支持订阅指定流（SimulCast）
- **缺点：** 客户端需要下载 N-1 路流，下行带宽需求随人数增长
- **适用：** **当前主流架构**，视频会议（Google Meet/Zoom 均使用 SFU）、连麦直播

### 16.4 架构对比

| 架构 | 服务器参与 | 延迟 | 服务器压力 | 客户端带宽 | 适用规模 |
|------|----------|------|----------|----------|---------|
| Mesh（P2P） | 无 | 最低 | 无 | 随人数增加 | ≤4 人 |
| MCU | 混流 | 中 | 极高 | 固定（1上1下） | 多人/低带宽 |
| SFU | 转发 | 低 | 中等 | 上行固定，下行随人数 | **主流，10～100人** |

### 16.5 主流 SFU 开源方案

| 项目 | 语言 | 特点 |
|------|------|------|
| Mediasoup | Node.js + C++ | 高性能，低级 API，需自己实现信令 |
| Janus | C | 功能完整，支持多种 WebRTC 插件 |
| Jitsi Meet | Java/Node.js | 完整视频会议系统（开箱即用） |

## 十八、技术选型速查表

### 直播场景选型

| 需求 | 推荐方案 |
|------|---------|
| 推流协议 | RTMP（稳定网络）/ SRT（弱网跨公网）|
| iOS 播放 | HLS（首选）/ HTTP-FLV（flv.js辅助）|
| Android 播放 | HTTP-FLV / HLS，配合 ijkplayer |
| Web 播放 | HTTP-FLV + flv.js（低延迟）/ HLS（兼容性） |
| 极低延迟互动（<1s） | WebRTC |
| 主播美颜 | GPUImage（iOS）/ OpenGL ES / GPUPixel（跨平台）|
| 服务端 | SRS（开源首选）/ Nginx-RTMP（简单场景）|
| 多方连麦 | SFU 架构（Mediasoup / LiveKit）|

### 视频编码选型

| 优先级 | 标准 | 理由 |
|--------|------|------|
| 第一 | H.264 | 最广兼容，直播推流标准 |
| 第二 | H.265 | 4K 内容、带宽受限 |
| 第三 | AV1 | 大规模点播、免费开源 |
| 未来 | H.266 | 等待硬件普及 |

### 音频编码选型

| 场景 | 推荐 |
|------|------|
| 直播推流 | AAC-LC |
| 实时通话/WebRTC | Opus |
| 音乐存档 | FLAC（无损）/ AAC（有损）|
| 院线音效 | AC-3 / EAC-3 |
