### 字符、字符集与编码

字符：一个可显示/可处理的符号。比如：A、中、😀

字符集：字符 和 数字（码点）的对照表

编码：码点如何转换成字节序列存进内存/文件

## 1. 字符

字符是人类书写系统中最小的抽象单位。

- 字母：`A`、`b`、`ñ`
- 数字：`1`、`2`
- 符号：`@`、`€`、`♠`
- 汉字：`中`、`文`
- 表情：`😀`、`🐱`

字符是概念层面的东西，就是一个符号本身

## 2. 字符集

字符集干一件事：给每个字符分配一个唯一的整数编号，这个编号叫做码点（Code Point）。

字符集就是一张对照表：

```
字符  →  码点（整数）
A    →  65
B    →  66
中   →  20013
😀   →  128512
```

字符集不管这个数字怎么变成字节，它只负责"字符←→数字"的映射。

几个重要的字符集：

#### ASCII（1963年）

最早的字符集，只收录了128个字符（英文大小写、数字、标点、控制字符）。它的码点范围是 0～127，用7个二进制位就能表示全部字符。

```
'A' → 65
'a' → 97
'0' → 48
'\n'→ 10（换行控制符）
```

ASCII 的影响极其深远，几乎所有后来的字符集，前128个字符都和 ASCII 保持一致。

#### Unicode（1991年至今）

ASCII 只能表示英文，全球各地的语言——中文、日文、阿拉伯文……都有自己的字符集，互相不兼容，造成了巨大的混乱。

Unicode 的目标是：把全人类的所有字符收进一张表。

现在 Unicode 已收录超过14万个字符，码点范围是 `U+0000` 到 `U+10FFFF`（十六进制表示）。

Unicode 用"平面（Plane）"来组织这些字符，每个平面包含65536个字符（`0x0000`～`0xFFFF`）：

```
平面0：U+0000 ～ U+FFFF   → 基本多文种平面（BMP）
        ↑ 包含绝大多数常用字符：英文、中文、日文、韩文……

平面1：U+10000 ～ U+1FFFF → 包含古文字、部分 emoji
平面2：U+20000 ～ U+2FFFF → 更多生僻汉字
……以此类推，共17个平面
```

#### GB2312 / GBK / GB18030

中国国家标准字符集系列，专门收录汉字：

- GB2312（1981）：收录6763个常用汉字
- GBK（1993）：扩展到2万多汉字
- GB18030（2000）：进一步扩展，兼容 Unicode 的字符范围

## 3. 编码

有了字符集，下一个问题是：这个数字怎么存进计算机？

这就是编码的工作：把码点转换成字节序列。

#### ASCII 的编码（最简单的情况）

ASCII 字符集的码点范围是 0～127，只需要7个二进制位，直接用1个字节存就够了：

```
'A' → 码点 65 → 字节 0x41 → 二进制 01000001
```

ASCII 的字符集和编码方式完全一一对应，所以人们通常不区分"ASCII字符集"和"ASCII编码"，直接说"用ASCII编码"。

#### Unicode 的三种编码方式

Unicode 的码点范围很大（0 到 0x10FFFF），一个字节存不下，所以 Unicode 设计了三种不同的编码方案，根据使用场景各有优劣：

UTF-32：最简单粗暴：

- 规则：每个字符固定用4个字节（32位）表示。

```
'A'  → U+0041  → 00 00 00 41（4个字节）
'中' → U+4E2D  → 00 00 4E 2D（4个字节）
'😀' → U+1F600 → 00 01 F6 00（4个字节）
```

- 优点：固定长度，计算极方便。想知道第100个字符在哪里？直接跳到第 99×4=396 字节处。
- 缺点：太浪费。一个英文字母 `A` 本来1个字节够了，现在要占4个字节，前3个字节全是0，浪费了75%的空间。
- 使用场景：在内存中处理字符串时有时会用（Python3 内部在某些情况下用 UCS-4，类似 UTF-32）；存文件、传网络几乎不用。

UTF-16：折中方案

- 规则：BMP内的字符（U+0000～U+FFFF）用2个字节，BMP以外的字符（U+10000～U+10FFFF）用4个字节（通过"代理对"机制实现）。

```
'A'  → U+0041  → 00 41（2个字节）
'中' → U+4E2D  → 4E 2D（2个字节）
'😀' → U+1F600 → D8 3D DE 00（4个字节，代理对）
```

- 优点：处理中文、日文等 BMP 字符时，每个字符2字节，比 UTF-32 省空间，且长度固定，遍历方便（只要内容在BMP内）。
- 缺点：英文内容下比 UTF-8 费空间；遇到 emoji 等补充字符就变成4字节，处理"代理对"逻辑复杂，是很多 bug 的来源。
- 使用场景：Windows 操作系统内部、Java 的 `char` 类型、JavaScript 的字符串，历史原因用了 UTF-16。

UTF-8：互联网的通用语

- 规则：用1到4个字节的变长编码，根据码点大小自动选择字节数。

| 码点范围                         | 字节数 | 字节模板                              |
| :------------------------------- | :----- | :------------------------------------ |
| U+0000 ～ U+007F（ASCII范围）    | 1字节  | `0xxxxxxx`                            |
| U+0080 ～ U+07FF                 | 2字节  | `110xxxxx 10xxxxxx`                   |
| U+0800 ～ U+FFFF（含大多数汉字） | 3字节  | `1110xxxx 10xxxxxx 10xxxxxx`          |
| U+10000 ～ U+10FFFF（emoji等）   | 4字节  | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

- UTF-8 最重要的特性：向下兼容 ASCII。
- 如果你的文本只包含 ASCII 字符（纯英文、数字），那么 UTF-8 编码出来的字节序列和 ASCII 编码完全相同，一个字节不多，一个字节不少。这使得所有原来只认识 ASCII 的老程序，可以无缝读取 UTF-8 编码的纯英文内容。
- 优点：省空间（英文1字节）、兼容 ASCII、自同步（可以从任意字节位置判断是否是字符起始位）
- 缺点：变长编码，想直接访问第100个字符，必须从头扫描（无法用偏移量直接跳转）。
- 使用场景：互联网标准，HTML/CSS/JSON 默认编码，Linux/macOS 默认，Python3 源代码默认，现代编程推荐首选。
